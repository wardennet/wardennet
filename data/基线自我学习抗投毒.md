你发现了一个非常经典且致命的陷阱——**"数据投毒导致基线漂移"**。在安全领域，这被称为 **"概念漂移（Concept Drift）对抗"** 或 **"自适应攻击（Adaptive Adversarial Attack）"**。

你的担心完全正确：如果攻击者知道你在用"全局404比率"当基线，他们只需控制100个肉鸡同时扫出大量404，就能把基线拉高，从而"洗白"后续的核心攻击流量。

要解决这个问题，**绝对不能只用"全局平均值"，必须引入"稳健统计学（Robust Statistics）"和"双层时序校验"**。下面给你一套工业级抗投毒的自学习架构：

---

### ?? 核心设计思想：放弃"均值"，拥抱"分布"

攻击者投毒的本质是**在数据集中注入离群值（Outliers）**。我们要做的，不是让模型"适应"这些离群值，而是让模型**自动识别并剔除这些离群值**，只学习"主流正常流量"的骨架。

---

### ??? 策略一：基于分位数的基线（替代平均值）

**不要计算所有请求的404比率，而是计算"每个IP的404比率"的分布分位数（如 P50, P90）。**

- **错误做法**：`总404数 / 总请求数`（容易被少数高频攻击IP拉高）。
- **正确做法**：假设1小时内你的网站有 10,000 个独立 IP 访问。你算出**每个 IP 各自的 404 比率**，然后取这 10,000 个比率的 **中位数（P50）** 和 **上四分位数（P75）**。

| 场景 | 全局均值（被投毒） | IP维度的中位数（抗投毒） |
| :--- | :--- | :--- |
| 正常时（无攻击） | 5% | 5% |
| 100个攻击IP疯狂扫404（占比1%） | 被拉高到 **30%** | 依然保持在 **5.2%**（因为99%的正常IP没变） |

**判定逻辑**：当某个 IP 的 404 比率 > 全局 P75 的 **3倍** 时，判定为异常。因为投毒者的数据被压缩到了"上尾"，不影响中位数和P75。

---

### ??? 策略二：加权过滤 + 截尾均值（Truncated Mean）

在计算基线之前，先按**请求量**对 IP 进行分层过滤：

1. **剔除"低频IP"**：只访问了 1~2 次且都 404 的 IP，对基线贡献为 0（低频没有统计意义）。
2. **截尾处理（Winsorization）**：在计算整体基线之前，**人为将前 1% 高404率的IP剔除**（视为潜在投毒者），只用剩余 99% 的流量计算基线。
   - *代码逻辑*：按IP的404率排序，取 `[1%, 99%]` 区间内的数据进行平均。即使攻击者涌入，只要他们数量不超过总IP数的1%，就完全不影响基线。

---

### ??? 策略三：双缓冲 + 漂移检测（终极抗投毒）

这是最接近你"自学习"初衷，且最稳健的方案。核心是**引入"时间窗口对比"机制**，拒绝"突变式学习"。

#### 机制设计：
1. **长时基线（A）**：过去 **7天** 的稳健基线（中位数）。更新速度慢，代表网站的"免疫记忆"。
2. **短时窗口（B）**：最近 **1小时** 的实时数据。

**更新策略（CUSUM 累积和检测）**：
- 每隔 10 分钟，计算 B（1小时窗口的404中位数）。
- 如果 `|B - A| / A < 10%`（波动在合理范围），则将 B 平滑融入 A（A = 0.99*A + 0.01*B，即正常学习）。
- 如果 `|B - A| / A > 30%`（发生剧烈突变）：
  - **触发保护机制：立即暂停基线的自动更新！**
  - 判定当前时段为"异常攻击窗口"，此时学习到的 B 是"毒数据"，直接丢弃。
  - 持续封锁直到 B 回落到 A 附近，才重新开启学习。

**效果**：攻击者为了投毒，必须持续高强度扫描 **7天以上** 才能缓慢拉高基线，而这期间他们的扫描行为早就被你的 L1/L2 规则封禁了，形成攻防闭环。

---

### ??? 策略四：引入"多样性熵"辅助修正（检测是否被投毒）

攻击者投毒时，虽然 404 比率高了，但他们请求的 **路径分布（URI Distribution）** 和正常用户完全不同。

- **正常基线**：请求路径遵循 Zipf 分布（少量热门页面占 80% 流量）。
- **投毒扫描**：请求路径是均匀分布（遍历字典，每个路径只试一两次）。

**加入特征**：在计算基线时，不仅要看 404 比率，还要看 **"URI 集合的香农熵"**。
- 如果当前窗口的 URI 熵值 **远大于** 历史基线熵值（说明有人在乱扫乱撞），则自动将基线更新权重降为 0（拒绝学习）。
- 这相当于给自学习机制加了一把"锁"，只有流量"有序"（熵值正常）时，基线才允许更新。

### ?? 最终推荐的技术架构（离线计算）

由于这些计算涉及全量 IP 的分位数和熵统计，不建议在 Agent 实时流中计算（开销太大）。推荐采用 **双轨制**：

| 模块 | 计算周期 | 技术栈 | 用途 |
| :--- | :--- | :--- | :--- |
| **在线 Agent** | 实时（毫秒级） | 使用**上一次离线算好的静态阈值**（如：404率 > 15% 即为异常） | 快速封禁，不参与学习 |
| **离线计算器** | 每 5 分钟 / 每小时 | Python/Pandas 读取最近的日志，计算分位数、熵值、执行漂移检测 | 计算新的阈值，推送给 Agent |

**离线计算器（Python伪代码）**：
```python
import pandas as pd
from scipy.stats import iqr

# 1. 读取最近1小时日志，按IP分组
df = pd.read_log('access.log')
ip_stats = df.groupby('ip').agg(
    total=('status', 'count'),
    p404=('status', lambda x: (x==404).sum()/len(x)),
    uri_entropy=('uri', lambda x: entropy(x.value_counts(normalize=True)))
)

# 2. 剔除低频IP（少于10次请求）
ip_stats = ip_stats[ip_stats['total'] >= 10]

# 3. 稳健基线（截尾均值，剔除上下1%极端值）
baseline_404 = ip_stats['p404'].quantile(0.98)  # 取P98作为封禁阈值
baseline_entropy = ip_stats['uri_entropy'].median()

# 4. 漂移检测（与历史基线对比）
historical_404 = redis.get('baseline_404')
if abs(baseline_404 - historical_404) / historical_404 > 0.3:
    # 突变！拒绝更新，发出告警
    send_alert("基线漂移异常，疑似大规模投毒攻击")
else:
    # 正常更新
    redis.set('baseline_404', baseline_404 * 0.9 + historical_404 * 0.1)
```

### ?? 避坑指南：关于"自我学习"的终极哲学

你必须接受一个事实：**完全自适应的无监督系统，在强对抗环境下必然失效（Adversarial Robustness 理论）。**

因此，给生产系统的建议是：
1.  **设定"绝对硬阈值"**：无论基线怎么漂移，404率 > 70% 直接封（这是不可能误杀的）。
2.  **保留人工校对锁**：当检测到基线发生大幅漂移时，自动切换为"只告警，不学习"模式，发送邮件通知管理员人工确认。
3.  **周期性重置**：每月 1 号强制重置基线为"出厂设定"（或重新读上一周的干净数据），防止基线缓慢漂移到不可用状态。

这套组合拳打下来，攻击者要想投毒，就必须控制**上万个**不同 IP 且模拟出真实的 Zipf 分布（热门路径），这成本比直接攻击网站本身还要高——这就是你要的"攻防不对等"。
