在如此优秀的底子上，我以“极端生产环境”和“高级持续威胁（APT）对抗”的视角，挑几个可以进一步**锦上添花**的优化点：

### 1. 云端增量 Diff 的“惊群”与“洪流”风险
你的 `diffLoop` 默认 10 分钟拉取一次。假设你有 1 万台 Agent，云端在某一刻生成了一个包含 5000 个新威胁IP的 `incr_list`。

- **潜在风险**：这 1 万台 Agent 会在同一时刻（`10:00:00`）向云端发起 Diff 请求，导致云端 API 瞬间被打爆（惊群效应）。同时，这 5000 个IP下发给每台 Agent 的 `ApplyCloud` 会导致所有服务器的 `ipset` 在同一时间剧烈抖动，消耗大量 CPU。
- **优化建议**：
  - **Jitter（抖动）机制**：Agent 的 `diffLoop` 不要固定 `10min`，而是 `10min + rand(0, 60s)`，将请求在时间轴上打散。
  - **云端限流与分页**：`incr_list` 不要一次性全量下发。云端可以设置 `max_incr_size=200`，如果超过则强制把 `NeedBase` 设为 `true`，让 Agent 拉取全量快照（`ipset swap`），这样比逐条下发几千条规则要高效得多。

### 2. 日志解析的单点故障（Log Rotation 与 Backpressure）
你的 `logparser` 使用了 `Tail` + 位置续读。但在高并发下，如果 Agent 的 `Detector.Process()` 处理速度跟不上日志写入速度（背压），`Tail` 读取的行会堆积在 Channel 里。

- **潜在风险**：如果 Channel 满了，Go 的日志读取 goroutine 会被阻塞，导致 `access.log` 文件句柄堆积，甚至引发 `logrotate` 重命名失败，磁盘被撑爆。
- **优化建议**：
  - 引入 **Ring Buffer + Drop** 策略。当背压超过阈值时，主动丢弃日志行并记录 `dropped_count` 指标，而不是阻塞文件读取。
  - 明确处理 `logrotate` 的 `IN_MOVED_TO` 事件。当前只靠位置续读，如果日志被 `mv` 走后新文件创建，需要确保 `Tail` 能无缝切换到新 inode。

### 3. BodyScanner 的性能“死穴”
你的 `BodyScanner` 支持 JSON/Form 正则匹配和文件上传拦截。这是防御 SQLi 的利器，也是最容易拖垮 Agent 的地方。

- **潜在风险**：攻击者发送一个 **100MB 大小的 POST 请求**（包含大量垃圾字符）。你的 `BodyScanner` 如果读取并编译整个 Body 去做正则匹配，会导致 Agent 内存暴涨，甚至 OOM（内存溢出）。
- **优化建议**：
  - 严格限制 **`MaxBodyScanSize`**（例如 10KB 或 100KB）。对于超过此大小的请求体，直接跳过正则扫描（因为真正的 SQL 注入极少会在超大包体里），只记录长度特征。
  - 文件上传拦截使用 `io.LimitReader` 读取前 512 字节判断 MIME 即可，不要读全量。

### 4. 一致性模型（Consistency）对 API 网关的误伤
你的 5 维一致性模型会给路径集中度高、无 4xx 的 IP 打上 `BENIGN` 标签降权。这非常棒，但有一个例外：**微服务 API 网关**。

- **潜在风险**：合法的后端微服务（比如 CronJob 或 K8s 的 Pod）通过网关相互调用，它们的路径极其集中（只有 `/internal/health` 或 `/api/v1/sync`），且全是 GET/POST。这种模式在一致性模型眼里极其像“定向扫描器”。
- **优化建议**：增加 **`TrustedSubnet`（可信内网段）** 配置。对于来自 `10.0.0.0/8` 或 `192.168.0.0/16` 的内部流量，直接绕过 Consistency 和 Scorer 的严厉打分，只对公网 IP 执行全量检测。

### 5. 云端私有池（Private Pool）的“自我投毒”盲区
虽然你设计了双池隔离，且全局池需要 2 个付费租户交叉验证，但私有池（`threats_private`）是**“只对当前租户可见”**且**“Agent 拉取后直接参与本地决策”**的。

- **潜在风险**：如果攻击者拿到了单个租户的 `Agent-Secret`，他可以伪造大量虚假的 `LocalRiskScore=100` 的事件上报给云端。虽然这些假事件进不了全局池（因为只有1个租户），但它们**会进入该租户的私有池 `threat_scoring`**。随后该租户自己的 Agent 拉取 Diff 时，会看到这些假的高分 IP，并直接在自己的服务器上封禁。攻击者成功实现了**“定向自毁”**。
- **优化建议**：**Agent 在 Apply 私有池评分时，必须结合本地 Detector 的 `baseline` 进行二次校验**。即决策公式 `composite = cloud_score × 0.4 + local_freq_score × 0.3 + detector_score × 0.3` 中，如果 `cloud_score` 很高，但本地最近 5 分钟内完全没有见过这个 IP 的任何访问日志，则 Agent 应直接忽略这条云端指令（因为攻击者没有真的打过来，只是伪造了上报）。

### 6. IPv6 与 CIDR 聚合
你的 L2 威胁判定（/24 子网）目前只针对 IPv4（因为拆分了 `ip.split(".")[:3]`）。

- **潜在风险**：面对 IPv6 洪流攻击，/24 不再适用，且 `ipset` 的 `hash:net` 虽然支持，但云端聚合逻辑会报错。
- **优化建议**：在云端聚合器中增加 IP 版本判断，对于 IPv6 采用 `/64` 子网作为 L2 聚合单位。
