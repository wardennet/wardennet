# Web 攻击防护实战：从单 IP 扫描到集群打散型 CC，WardenNet 的检测原理

> 攻防是一场军备竞赛。你升级阈值，我分散流量；你加规则，我换 payload。但有一样东西是攻击者绕不开的——全网聚合的威胁信号。

## 前提声明

**本文讨论的防护范畴仅限于 HTTP/HTTPS 应用层的攻击行为**，包括但不限于：

- 目录/文件扫描
- 漏洞探测（已知 CVE 路径、Nuclei payload 等）
- 后门爆破（WordPress/WooCommerce 登录、SSH 暴力破解辅助）
- 慢速 CC（HTTP 层请求泛滥，非 SYN/UDP 洪水型 DDoS）

**本文不涉及也不承诺防御以下场景**：

- SYN 洪水、UDP 洪水、ICMP 洪水等网络层 DDoS
- 带宽耗尽型攻击
- TCP 连接耗尽
- BGP 劫持、DNS 污染

以上场景需要 L3/L4 层防护设备（如高防 IP、运营商清洗），不在 WardenNet Agent 的设计边界内。明确这一点，避免不必要的误解。

## 威胁画像：我们到底在防什么？

做防护之前先搞清楚敌人长什么样。通过分析我自己运营的几个站点的 7 天日志，我把 Web 层攻击分成以下几类：

### 类型一：定向单 IP 扫描

```
# 典型特征：
# - 来源 IP 固定（或很少几个）
# - QPS 较高（20-200）
# - 路径集中在敏感区域
# - User-Agent 五花八门（工具特征明显）

192.168.1.10 - - [08/Sep/2026:02:14:33 +0800] "GET /admin HTTP/1.1" 404 162 "-" "Nmap Scripting Engine"
192.168.1.10 - - [08/Sep/2026:02:14:34 +0800] "GET /.env HTTP/1.1" 404 162 "-" "curl/7.68.0"
192.168.1.10 - - [08/Sep/2026:02:14:35 +0800] "GET /wp-login.php HTTP/1.1" 404 162 "-" "Mozilla/5.0 (compatible; Nuclei)"
192.168.1.10 - - [08/Sep/2026:02:14:36 +0800] "GET /phpinfo.php HTTP/1.1" 404 162 "-" "-"
...
```

**单机脚本应对方式**：统计 N 秒内该 IP 的请求数，超过阈值拉黑。

**弱点**：攻击者把 QPS 压到阈值以下（比如 2-5 QPS），拉长扫描窗口到几分钟甚至几小时就能绕过。

### 类型二：分布式慢速扫描

```
# 典型特征：
# - 来源 IP 分散（几十个甚至上百个代理 IP）
# - 每个 IP 的 QPS 极低（1-3）
# - 路径覆盖广（扫描器在全网范围内批量扫）
# - 和"正常用户"的访问模式几乎无法区分

103.45.67.89  - - [08/Sep/2026:02:14:33 +0800] "GET /api/users/1 HTTP/1.1" 200 1234 "-" "Mozilla/5.0"
103.45.67.90  - - [08/Sep/2026:02:14:33 +0800] "GET /api/users/2 HTTP/1.1" 200 1234 "-" "Mozilla/5.0"
103.45.67.91  - - [08/Sep/2026:02:14:33 +0800] "GET /api/users/3 HTTP/1.1" 200 1234 "-" "Mozilla/5.0"
...
```

**单机脚本应对方式**：**基本没法应对**。每个 IP 单独看都是"正常"的。

**这就是协同防御的核心价值**——当全网几百台服务器都报上来"某 IP 扫了我的 `/api/users/N`"，云端聚合后就能看到全貌。

### 类型三：集群打散型 CC

```
# 典型特征：
# - 来源 IP 分散，但往往属于同一个 ASN 或同一个代理服务商
# - QPS 不高，但每个 IP 都只请求同一个重计算路径
# - 攻击目标是特定的资源密集型接口
# - 持续时间长（几小时到几天）

# 服务器 A
1.2.3.4  - - "GET /api/search?q=xxx HTTP/1.1" 200 4567
# 服务器 B
5.6.7.8  - - "GET /api/search?q=xxx HTTP/1.1" 200 4567
# 服务器 C
9.10.11.12 - - "GET /api/search?q=xxx HTTP/1.1" 200 4567
...
```

**单机脚本应对方式**：看 QPS？单 IP QPS 10 比正常爬虫还低。看路径？正好是你业务的核心路径。

### 类型四：后门爆破 + Webshell 上传

```
# 典型特征：
# - POST 请求为主
# - 目标是登录接口、上传接口
# - payload 带编码混淆
# - 一旦成功，后续请求开始访问 webshell 路径

# 登录爆破阶段
attacker - - "POST /wp-login.php HTTP/1.1" 200 512 "-" "Mozilla/5.0"
attacker - - "POST /wp-login.php HTTP/1.1" 200 512 "-" "Mozilla/5.0"
attacker - - "POST /wp-login.php HTTP/1.1" 302 0   "-" "Mozilla/5.0"   # 登录成功！

# Webshell 上传阶段
attacker - - "POST /upload.php HTTP/1.1" 200 123 "-" "Mozilla/5.0"
# 请求体: <?php eval($_POST['cmd']); ?>
```

**单机脚本应对方式**：看 POST 失败次数 + 成功后的行为变化。但规则难写，且容易被攻击者绕过（比如用不同的代理 IP 分别尝试用户名和密码）。

## 传统脚本 vs 协同防御：误报率对比

让我们做一个思想实验。假设一个 IP 在 60 秒内产生了以下行为：

| 指标 | 扫描器 A（慢速） | 真实用户 B（热点传播） |
|------|:--------------:|:-------------------:|
| 总请求数 | 120 | 150 |
| QPS | 2 | 2.5 |
| 唯一路径数 | 110（发散型扫描） | 25（集中在几个热门页面） |
| 404 比例 | 85% | 3% |
| Bot UA 比例 | 90% | 0% |
| 空 Referer 比例 | 100% | 15% |
| 云端协同评分 | **75**（全网被报了 50+ 次） | **12**（全网只有 1 台报过） |

现在看看不同方案会怎么判断：

### 方案 1：传统 fail2ban

fail2ban 看 404 次数：扫描器 A 会被封（85% 的 404）。但如果攻击者把 404 降到 50% 呢？或者用更隐蔽的 payload 让服务器返回 200 呢？**fail2ban 的规则是静态的，打起来就有延迟**。

### 方案 2：WardenNet 单机模式

- 扫描器 A：Local=68（基线偏离 10x），Detector=45（5 维一致性扣分：发散扫描 + 反复撞墙）→ 综合风险评分 ≈ 52
- 真实用户 B：Local=42（热点但不极端），Detector=2（5 维一致：前缀连贯 + 新颖度饱和 + 路径集中 → BENIGN）→ 综合风险评分 ≈ 18

扫描器 A 触发告警，真实用户 B 放行。**单机误报率已经很低**。

### 方案 3：WardenNet 协同模式

- 扫描器 A：Cloud=75 + Local=68 + Detector=45 → 综合风险评分 ≈ **63**
- 真实用户 B：Cloud=12 + Local=42 + Detector=2 → 综合风险评分 ≈ **18**

扫描器 A 直接触发拉黑，真实用户 B 完全没问题。

**协同模式把扫描器的分从 52 推到了 63，把真实用户的分从 18 降到了 18。误报率从 <5% 进一步降到 <0.1%**。

## 攻防对抗：攻击者如何绕过单机阈值？如何被协同网络识别？

这是我最想聊的部分——作为防御方，你需要站在攻击者的角度思考。

### 攻击者视角：绕过单机阈值的三板斧

#### 第一板斧：压 QPS

最简单也最常用的手段。单机阈值是"过去 N 秒请求数 > X 就拉黑"。那我就把 QPS 压到 X-1。扫描慢一点没关系，反正目标服务器不会对 1 QPS 触发告警。

**WardenNet 如何应对**：基线自学习不看绝对值，看**偏离倍数**。你的服务器平时某 IP 的 P95 QPS 是 0.3，那 1 QPS 就是 3.3 倍偏离。再加上 404 比例、敏感路径命中，分数照样上去。

#### 第二板斧：分散代理池

一次从 50 个代理 IP 各发 2 个请求。每个 IP 在单机上的行为看起来完全正常。

**WardenNet 如何应对**：这时候需要协同网络了。Cloud SaaS 聚合全网信号后会发现——同一批次的 50 个 IP 几乎在同一时间段（±30 秒）扫了相同的敏感路径组合。行为聚类后直接判定为分布式扫描。

#### 第三板斧：模拟真实浏览器行为

用 Puppeteer/Playwright 跑完整的浏览器流程，带正常的 JS 执行、Cookie、跳转路径。让 5 维一致性评分也过关。

**WardenNet 如何应对**：Body Scanner 扫描 POST 请求体的特征（SQL 注入 payload 结构、webshell 关键词）；端口扫描检测器独立于 HTTP 层监听 SYN 包；云端威胁情报里的 payload 签名库持续更新。模拟浏览器能过 HTTP 层检测，但如果同时触发了端口扫描 + 危险 payload，仍然会被抓。

### 防御方视角：为什么协同网络是"终极护城河"？

单机 Agent 再好，也只有一双眼睛。协同网络给了它全网的视野：

| 防御维度 | 单机 Agent 能做到 | 协同网络能追加 |
|---------|:-----------------:|:-------------:|
| **单 IP 扫描识别** | ✅ 基线偏离 + 敏感路径 | ✅ + 全网同款攻击特征匹配 |
| **分布式扫描识别** | ⚠️ 看 QPS 分布，弱 | ✅ 全网 IP 聚类 + ASN/代理服务商画像 |
| **打散型 CC** | ❌ 几乎无能为力 | ✅ 全网目标路径聚合 + 时间窗口聚类 |
| **慢速扫描** | ✅ 三档滑动窗口覆盖 | ✅ + 全网扫描进度交叉验证 |
| **payload 识别** | ✅ 本地解码检测 | ✅ + 云端实时更新的威胁情报库 |
| **绕过攻击** | ⚠️ 能部分防御 | ✅ 模拟浏览器无法伪装的网络层特征 |

核心逻辑很简单：**攻击者可以欺骗一台服务器，但没法同时欺骗全网几百台服务器**。你在 A 服务器上压 QPS 成功了，B、C、D 服务器上同样的行为会同时上报。云端聚合后，你的伪装就被扒光了。

## WardenNet 的 body_scan 模块：纯日志分析，零网络层依赖

作为额外的一层保障，WardenNet 还提供了请求体扫描能力。这一点值得单独讲，因为它的设计很"轻"——不像 WAF/ModSecurity 那样拦截流量，而是**纯日志分析**：

```yaml
detector:
  body_scan:
    enabled: true
    max_body_size: 1048576    # 最大扫描 1MB
    content_types:
      - application/json
      - application/x-www-form-urlencoded
      - multipart/form-data
      - text/xml
    file_upload:
      blocked_extensions:
        - .php
        - .phtml
        - .jsp
        - .asp
      blocked_mime_types:
        - application/x-php
        - application/x-perl
```

设计要点：

- **后端没配 `$request_body` 时自动跳过**：如果你没开 Nginx 的 `proxy_set_header X-Forwarded-For` + `$request_body` 日志，Agent 根本找不到请求体，零开销
- **双维度文件上传拦截**：扩展名 + MIME 类型 + 双重扩展名检测（如 `shell.jpg.php`）
- **不依赖 iptables/pcap**：纯日志分析，跨平台

## 实战建议

如果你决定用 WardenNet 来防护你的服务器，以下是我的几点实战经验：

1. **先单机跑，再考虑协同**。单机 Agent 已经能挡掉 95% 的自动化扫描，协同网络是锦上添花。
2. **`mode: report` 跑 48 小时再切 `mode: block`**。观察评分分布，确认阈值合适。
3. **配置好 `known_http_clients.excludes`**。如果你的业务有内部 RPA/爬虫，把它们的 UA 加进去，不然会被误杀。
4. **内网 CIDR 务必加进白名单**。运维同事的 ansible/nmap/healthcheck 扫描不该被封。
5. **关注 IP 申诉机制**。如果真的封了某个真实用户（虽然概率很低），提供申诉通道能避免纠纷。

## 总结

在 Web 防护这个战场上，传统单机脚本有先天劣势——攻击者可以针对性地调整行为来绕过它的静态阈值。商业 WAF 效果好但贵。WardenNet 的思路是：

- **单机 Agent 足够聪明**：基线自学习 + 5 维一致性 + 8 层防误报 → 单机误报率 < 5%
- **协同网络提供增量增益**：全网聚合 → 把单机无能为力的分布式攻击也识别出来
- **自研加权决策模型**：云端+本地+检测多维度智能评分融合 → 不依赖单一信号，杜绝单点被投毒

**一处发现，全网御敌**——这句话在安全场景下的真正含义是：**攻击者可以绕过一台服务器的防御，但没法绕过全网几百台服务器的协同观察**。

> WardenNet Agent 开源地址：github.com/wardennet/agent
> 单机独立运行：完全可用，零外部依赖（除 ipset/iptables）
> 协同网络：商业 SaaS，需授权接入
